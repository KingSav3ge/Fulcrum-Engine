## 2. Merge and reconcile

All **228/228 original held families now have an individually named proposed qualitative dossier** (36 R1 + 192 R2). **This does not mean that all 228 have become ready for activation or eligible for source deprecation.** The 51 selected source-backed contracts and the entire 228 hold status remain unchanged in the normative registry.

Each R2 dossier uses the source registry's alias, source rows and structured source fields; separates these from new proposed operational interpretations; names one parent Core record owner/interface; distinguishes useful output from mere service/equipment/site classification; specifies actual inputs, feasibility limits, state changes, non-effects, failure and meaningful reassessment; and includes paired positive/negative acceptance specifications.

Most novel procedural material is intentionally **genre-neutral but not universalized Core**. It binds to Core owner records and the native genre/model; it does not insert new combat dice, armor ratings, supply generation, injury formulae, field capacity, crew statistics, gas-flow or other numerical constants.

## 3. Causal design dispositions

| Finding | Decision | Reason |
|---|---|---|
| Many held source rows already contain usable functional descriptions and essential interfaces | Expand | Preserve the actual source claim and translate only as proposed qualitative content |
| Ratings/rates/thresholds missing | Keep calibration dependency | Inability to calculate a specific output is not license to invent a default |
| Stock and service may be represented from different viewpoints | Separate views; one owner | Inventory balance K-STOCK, service allocation K-NET/K-WORK; never create both as stock |
| Facility, equipment and organization may describe overlapping capability | Bind references, no duplicate construction | A building, tool and team are not each an independent production grant |
| Fantasy attack-mode selectors already share physical parent | Preserve | Do not convert mode entries into extra gear, attacks or universal damage |
| Hospitals/medical stocks, fuels, water/food treatment and other restricted specialist uses | Keep native expert gate | Ordinary content classification is not authority to apply specialized effects |
| Hazard/crisis templates can be mistaken for actual occurrence | Enforce occurrence gate | Templates neither spawn emergencies nor resolve them automatically |
| Population movement and communications can be confused with reports | Preserve transit/receipt | Facts move through actual pathways; receipt does not retroactively alter source action |
| Existing canonical checksums/statuses are pinned | No in-place edits | Replacement needs separately versioned family IDs and opt-in migration |

## 4. Acceptance levels and limitations

**Completed by R2:** 192 unique source-backed qualitative dossiers with paired case specifications and explicit parent ownership. 228/228 formerly held definitions are now covered by R1 or R2 authored contracts. Normative Core and catalogue files are unchanged. Machine checks verify source-field transcription, alias resolution, case presence, document/reference completeness, original-file integrity and non-promotion.

**Not established:** numeric calibration, real equipment/species performance, independent live simulation, external technical/medical certification, cross-genre balancing, campaign adoption, implementation of all 384 individual positive/negative tests in a full runtime, or source deprecation.

**Synthetic scenarios executed in a standalone fixture:** conservation of lot transfers, replay idempotence, bounded shared throughput, finite energy, communication receipt delay, population transit conservation, preservation of unresolved cold-chain quality, uncommissioned-service exclusion, pharmaceutical-lot specificity, and competing resource claims. These fixtures do not evaluate physical water quality or actual refrigeration performance. Results concern accounting contract logic only, not physics/medicine accuracy.

## 5. Proposed future per-family promotion gate

1. Compare each draft against its source payload, source status, adapter and applicable campaign model; fix conflicts rather than deleting source distinctions.
2. Establish all material numeric/operating parameters in the applicable environment, with units, valid ranges, provenance and actual owners; explicitly mark optional/unavailable fields.
3. Execute entry-level positive/negative cases in a compatible active engine, including scarcity, Mixed, shared capacity, simultaneity, scale changes and repeated events; verify no duplicated resource or action.
4. Publish a **new per-definition immutable revision** with alias/checksum compatibility and source-crosswalk disposition. Do not relabel @0.2 as newly calibrated.
5. Seek explicit adoption; migrate individual campaign configurations prospectively only when authorized. Historical state and past consequences remain pinned.

## 6. Migration impact

Zero normative migration. The additive R1 and R2 files may be omitted entirely by an existing deployment with no semantic change. Importing an R2 proposal into a future release is a separate action requiring an explicit receiving adapter and release manifest update.
