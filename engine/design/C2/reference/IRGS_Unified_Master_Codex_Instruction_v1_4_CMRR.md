# PART I — CMRR RECONCILIATION

## 1. Primary Directive

Apply:

**Compare → Merge → Reconcile → Resubmit (CMRR).**

Develop IRGS into a persistent, autonomous, extensible world-simulation engine capable of supporting individual roleplaying, households, settlements, governments, economies, military institutions, civilizations, and specialized genres.

The system must provide a coherent player experience through:

**Content Library → Campaign Selection → Historical Entry → Starting Scenario → Character Creation → Campaign Initialization → Story → Gameplay → Save/Resume → Chronicle → Progression → Continued World Simulation.**

The following principles are mandatory:

- Core determines what actually happens.
- Agency determines what autonomous actors attempt.
- Presentation communicates established and appropriately reported events.
- Saves preserve authoritative state.
- Chronicle presents established history and legitimately available information.
- Progression describes mechanically supported development.
- Genre foundations extend universal mechanics without replacing Core authority.
- Website workspaces expose the same persistent world through different authorized perspectives.

**IRGS must remain one simulation engine, not a collection of disconnected game systems.**

## 5. Authoritative Simulation Hierarchy

Preserve:

**Shared Core → Genre Foundation → Setting Module → Campaign Profile → Independent Campaign State**

### Core

Owns universal simulation functions including actors, identities, locations, resources, time, events, institutions, legal position, economy, households, population, military organization, information and physical effects.

### Genre Foundation

Supplies specialized mechanics, without independent authority over world state.

### Setting Module

Supplies setting-specific rules, institutions, technology, geography and content.

### Campaign Profile

Selects initial conditions, compatible rules, sources and gameplay configuration.

### Campaign State

Preserves the actual independent world produced by gameplay.

A published campaign is not the same thing as a player's playthrough.

Two playthroughs can share an initial campaign definition but must not share mutable state.

## 6. Three Operational Layers

### Simulation

Determines legitimate physical, institutional and mechanical outcomes.

### Agency

Determines what player-controlled and autonomous actors attempt.

NPC agency must consider actual knowledge, goals, obligations, capabilities, relationships, resources and circumstances.

### Presentation

Converts established simulation events into information appropriate for the player.

It may employ AI narration, dialogue and summarization, but must not independently commit authoritative world changes.

### Universal action pipeline

**Intent → Interpretation → Validation → Selected Resolution → Commit → Persistence → Scheduling → Information Distribution → Presentation → Chronicle**

The exact implementation may coordinate these operations transactionally, but the following invariants apply:

- No narrative description can create an authoritative effect.
- No event can become completed merely because it was requested.
- No failed narrator call can cause a committed action to execute twice.
- No save operation may silently advance world time.
- No character may access information unavailable to their perspective.
- No genre may create a duplicate population, resource or actor authority.

# PART VI — SAVES AND CAMPAIGN CONTINUITY

## 21. Save-System Objective

Saves preserve the actual simulated world and enable independent continuations.

Distinguish the following concepts.

| Concept | Definition |
|---|---|
| Campaign Definition | The registered campaign available for initialization |
| Playthrough | An independently initialized world |
| Save Revision | A persisted version of an actual playthrough state |
| Checkpoint | A confirmed revision designated for recovery or reference |
| Branch | Independent continuation of an eligible previous state |
| Archive | Playthrough retained outside the active list |
| Recoverable Trash | Removed playthrough eligible for restoration under supported rules |

Do not use these terms interchangeably.

## 22. My Campaigns — Player Experience

My Campaigns is the main interface for managing independent playthroughs.

Each playthrough card should display, where supported:

- Parent campaign.
- Playthrough name.
- Starting scenario.
- Controlled character or institution.
- Current world date.
- Starting historical entry.
- Current known location.
- Current branch.
- Most recent confirmed save.
- Latest action status.
- Compatibility state.

Prioritize **Continue Playing**.

Detailed save management should be available without obstructing ordinary resumption.

Displayed status must correspond to actual persistence acknowledgements.

Never show illustrative saves as genuine user history.

## 23. Automatic Persistence

Every committed authoritative action must become durably recoverable.

Use the existing persistence architecture, extending it as necessary.

Possible implementation techniques include event journaling, transaction records, validated snapshots or equivalent reliable mechanisms; select according to the existing repository.

Do not introduce redundant authoritative histories.

The critical requirement is:

**A reported successful commit must not disappear because presentation, navigation or a subsequent request failed.**

Maintain a reliable connection between:

- Request identity.
- Transaction identity.
- Authoritative commit.
- Persisted state.
- Event history.
- Presentation status.
- Client acknowledgement.

Implement idempotent recovery of submitted requests.

Repeated network submissions or retries must not duplicate effects.

## 24. Manual Saves and Named Checkpoints

Support manual checkpoint requests from consistent campaign states.

Players may name checkpoints.

A manual save must not:

- Advance simulation time.
- Cause NPCs to act.
- Refill resources.
- Heal characters.
- Create in-world events.
- Repeat unfinished actions.
- Invent a new player decision.

The checkpoint must reference a verified state.

If a save is requested while an operation is unresolved, use its existing request identity and known commit status to determine the legitimate recoverable state.

Do not create ambiguous revisions that imply uncertain effects definitely happened or definitely did not happen.

## 25. Save Recovery During Gameplay

Handle the following states explicitly.

| Condition | Required response |
|---|---|
| Waiting for player input | Normal confirmed checkpoint may be created |
| Unsubmitted action draft | Preserve draft separately |
| Submitted unresolved request | Preserve request identity and recovery state |
| Core effect committed | Persist committed result |
| Narration incomplete | Regenerate presentation without re-executing Core |
| Interrupted action | Preserve completed effects and outstanding obligations |
| Failure before commit | Retain player text without inventing an outcome |
| Persistence uncertainty | Verify the transaction record before retrying |
| Reload after interruption | Recover the confirmed state and pending operations |

A crashed narrator must never cause a financial transfer, injury, contract, item transfer or other already committed event to happen twice.

## 26. Branching

Branches are independent histories derived from eligible checkpoints.

A branch must retain:

- Unique branch identity.
- Parent branch or playthrough reference.
- Fork checkpoint.
- Applicable Core version.
- Genre and setting versions.
- Campaign and research editions.
- Authorized starting state.
- Independent subsequent history.

Creating a branch must not rewrite the parent.

After creation, branch histories evolve independently.

A character may die in one branch and survive in another without contradiction.

Preserve event identity and provenance sufficiently to identify shared history before the fork and independent history afterward.

The exact storage strategy must follow verified repository capabilities.

## 27. Resume, Restore and Branch

Distinguish three operations.

**Resume:** Continue the current confirmed state.

**Restore:** Change the active continuation to an earlier eligible revision.

**Branch:** Create an independent continuation from an eligible earlier revision.

Prefer branching as the ordinary safe alternative to destructive restoration.

Any operation that could supersede later history must clearly communicate the consequence and preserve appropriate recovery options.

Do not automatically merge independent branches.

## 28. Archive and Recoverable Trash

Archiving removes a playthrough from the active list without destroying its state.

Recoverable deletion must follow the existing supported retention and recovery rules.

Deletion must never silently destroy:

- Unrelated playthroughs.
- Shared campaign definitions.
- Technical content libraries.
- Other users' data.
- Independently owned files.
- Account-level entitlements.

Do not invent finalized retention periods or storage quotas absent from an approved policy.

## 29. Branching and External Rewards

Campaign branches must not duplicate account-level rewards, entitlements or externally redeemable balances.

The deferred Solo Universal Points system must remain disabled until separately qualified.

If a future system connects simulated wealth to account-level value, it must use a separate authoritative ledger with eligibility, provenance and duplicate-redemption protection.

Do not implement fictional currency-to-account currency conversion as part of this development round.

## 30. Save Compatibility

Every playthrough must retain sufficient provenance to identify:

- Parent campaign.
- Starting scenario.
- Historical entry.
- Research edition.
- Core version.
- Genre bindings.
- Setting modules.
- Content-library versions.
- Selected numerical models where relevant.
- Save schema version.
- Branch identity.
- Authoritative state and event references.

Later content updates must not silently rewrite established campaigns.

Support the following classifications where justified.

| Compatibility state | Meaning |
|---|---|
| Compatible | Can load and continue correctly |
| Migration available | Verified migration exists |
| Read-only recovery | Historical data can be inspected, but play cannot safely continue |
| Incompatible | Required support is unavailable |
| Damaged / Recovery needed | Validation failed or recovery is required |

Migration must be explicit, tested, backed up and reversible where technically practical.

## 31. Future Cloud Synchronization

Account-backed cloud saves and multi-device continuation are deferred unless already approved.

Future synchronization must identify divergent histories rather than silently overwriting or merging them.

A conflict should be resolved through authorized reconciliation or branch separation.

Do not merge two worlds by concatenating narrative transcripts.

# PART VII — CHRONICLE AND HISTORICAL MEMORY

## 32. Chronicle Objective

Chronicle preserves a readable, navigable history of the player's continuing world.

It must answer:

- What happened?
- When did it happen?
- Who was involved?
- What was learned?
- How reliable was the information?
- What changed?
- Which consequences remain relevant?

Chronicle must support both short sessions and campaigns lasting centuries.

It must not become an independent simulation database.

## 33. Chronicle Workspace

Under **Play → Chronicle**, implement nested sections for:

- Overview.
- Timeline.
- Character History.
- World Events.
- People & Institutions.
- Personal Journal.
- Correspondence & Reports.
- Historical Summaries.
- Search & Filters.

Support filtering by relevant:

- Dates.
- Actors.
- Places.
- Institutions.
- Event type.
- Source.
- Information reliability.
- Campaign branch.

A player must be able to inspect historical development without scrolling through the full gameplay transcript.

## 34. Event Time Versus Information Time

Distinguish:

1. Event occurrence.
2. Observation.
3. Transmission.
4. Receipt.
5. Later interpretation or reporting.

Example:

A military engagement occurs on one day.

A witness observes it.

A messenger departs later.

A commander receives the report days afterward.

The player learns of the engagement only when valid information reaches their controlled perspective.

Chronicle must preserve these distinctions.

Do not reveal the authoritative occurrence date, casualties, participants or outcome as confirmed character knowledge unless the perspective can legitimately know them.

## 35. Event Provenance

Chronicle records should reference appropriate source information:

- Actual event identity.
- Relevant actors.
- Relevant locations.
- Occurrence time.
- Observation time.
- Transmission and receipt where applicable.
- Source or witness.
- Information reliability.
- Actual outcome where permitted.
- Related institutional records.
- Related transactions or physical consequences.

An incorrect report is still a real report.

It must not overwrite the underlying event truth.

The interface should distinguish direct experience, reliable reports, rumours, disputed accounts, outdated information and unknown facts.

## 36. Structured Records and Narrative Summaries

Maintain separate:

**Structured Event Record:** Authoritative or legitimately filtered factual record.

**Narrative Summary:** Readable representation derived from available records.

Narrative summaries may describe patterns and historical significance.

They may not manufacture missing material resources, deaths, offices, marriages, wealth, laws or political outcomes.

A summary calling a decade prosperous does not establish that every household was wealthy.

Source references must remain available for relevant details.

## 37. Personal Notes and In-World Documents

Distinguish three record types.

### Player Note

A private interface annotation.

It may reference a person, place, event, date or campaign decision.
